# 一个医生，两种声音：研究材料包

在线入口：https://lllinyan.github.io/one-physician-two-voices/

仓库：https://github.com/lllinyan/one-physician-two-voices

当前材料版本：`build-2026-11-11.2`；内容版本：`draft-2026-11-04.1`。

这是公开托管的研究预览版。病例 A、B 的正文、依据和理由已写出，临床审核状态为 pending。正式模式暂未开放。备用空腹血糖病例保留为待临床拟稿的框架。

## 从哪里打开

1. 打开本文件同目录的 **index.html**，进入研究者入口。
2. 保持「内部预览」，填写参与者编号和场次编号，选择顺序与两个方向。
3. 点击「打开模拟问诊」。依次体验 AI 回复、医生回复和七个操作入口。
4. 两个情境的自由探索完成后，进入比较环节，再从研究者入口打开参与程度卡片。共享卡片展示窗口，完成前两轮后回到访谈。
5. 点击「打开设计工作台」。工作台自动使用这场的分身病例和建议方向。点击「打开展示窗口」，只共享展示窗口；备注、修改来源及控制项留在研究者窗口。
6. 设计完成后，由研究者在卡片控制窗口开放第三轮；收尾阶段再开放通用医疗AI比较。M6规定每一步的问法与时点。

构建器生成9个自包含HTML：研究者入口、固定材料渲染页、问诊在线／离线页、工作台控制／展示页、卡片控制／展示／打印页。参与者离线版本为`M2_prototype/offline.html`。直接打开文件可供单页走查；双窗同步建议从同一静态服务或托管地址打开。在本目录启动后访问`http://127.0.0.1:8765/`：

```sh
python3 -m http.server 8765 --bind 127.0.0.1
```

本机地址用于本机走查。远程参与者使用经过实测的静态托管地址，或下载离线文件后在已验证设备打开。手机能否保存和交回文件，应按实际机型演练并记录。

## 一场的操作顺序

主持人按M6进行，时间为10＋17＋13＋15＋20＋10分钟，共85分钟。原型在阶段A隐藏医生回复和操作区；口头完成初始理解后，提示参与者点击「查看医生回复」。意外提前点击，在研究者入口的人工曝光区选择意外揭示并登记。

「结束咨询」关闭当前情境的联系发送，仍可查看依据并进入下一情境。「退出本场研究」停止整场流程，主持人另行记录参与者对已有数据的保留或删除选择。

两情境完成会下载检查点，随后进行比较、真实经历和设计。卡片在两情境的自由表达之后才出现：第1轮回溯重建“只看到AI回复时”的理解，第2轮说明完整原型下的当前理解，两轮放在15分钟比较环节；第3轮在20分钟设计环节结束时开放，讨论自己最终设计。第2轮之后等待设计，第3轮之后等待收尾；两次继续均由研究者手动开放。收尾通用AI比较引用本场另一病例的接诊医生。

每轮可“跳过未答并继续”。空白／跳过与“不确定”分开记录；通用AI比较的空选择提交、跳过、尚未提交也分开保存。卡片JSON保存选项、轮次、原始陈述、比较陈述和事件；理由及主持提示记入M9“参与程度卡片”表与访谈笔记，统一标记`source=card_elicitation`。本轮卡片措辞为根据当前方案新拟的试访稿，试访后按版本管理修改。

工作台先留出自拟方案阶段，再按D1、D2、D3/D3′、D4、D5、D6固定顺序浏览。医学文字的改写另存为参与者提议，保留原文。完成方案后记录参与者确认；后续修改会要求重新确认。

收尾先完成告知，再导出、交回和现场打开核对。问诊日志导出保留在参与者页“更多”菜单。记录整场完成、交回状态或维护当前问诊记录时，先关闭同场参与者页，再从研究者入口打开`host=1`维护页；同场两个问诊窗口须避免同时写入。完成登记后导出最终记录。最后按同意书清理对应设备的本场记录及下载副本。

已确认的显示设置：审核说明14px；操作区标题“接下来你可以”；病情仅分段；桌面手机框最高844px，小屏自适应，真实手机整页滚动。人工曝光逐条保存到本机，结束时统一导出；本地保存失败时页面提供下载备份。

## 数据存在哪里

页面不发起数据请求，也不调用AI。四类记录在实际使用设备的浏览器本地保存：

- 问诊：`one-physician:session:<session_id>`。
- 工作台：`one-physician:studio:<session_id>`；展示窗口仅接收显示所需内容。
- 研究者入口人工曝光：`one-physician:researcher:<session_id>`。
- 参与程度卡片：`one-physician:cards:<session_id>`，持久记录保存在卡片控制窗口所在设备；展示窗口接收当前轮次内容并回传选择。

刷新或重开相同场次可恢复。切换浏览器、网址或设备时，本地记录不会自动转移。问诊支持先导出JSON再导入新页面，并保留已有事件编号、建立新记录段，记录切换原因和缺失范围。下载的离线HTML直接打开后，从“更多 → 载入已有演示记录”选择原JSON，核对恢复位置后继续；该入口保留导入校验，隐藏主持编号与控制项。在线参与者页默认隐藏导入，在线维护使用上述`host=1`入口。其他记录在原设备导出归档；卡片跨设备续做由主持人另行记录已完成轮次与缺失范围。配置、版本或同编号事件的内容发生冲突时，先核对原文件。

研究者入口可合并`participant_log`、`studio_design`、`researcher_log`和`card_elicitation`，按事件编号去重，并导出事件JSON与场次CSV。导入汇总只驻留当前页面内存；原始交回文件需按M8约定归档。自由文字保持在JSON中，CSV导出处理了可能被电子表格当作公式的文本前缀。

工作台的 PNG 是实际展示方案快照，JSON 保存配置、素材来源、修改发起者、原文与提议、修订记录、折叠状态和确认时间。点击「保存方案 ZIP（PNG + JSON）」后，页面先将可恢复方案持久化到本机，再尝试生成完整 PNG，最后一次下载一个 ZIP，内含同名 PNG 和记录最终图片结果的标准 JSON；例如 `P01_session01_studio_v2.zip` 内含 `P01_session01_studio_v2.png` 与 `P01_session01_studio_v2.json`。PNG 生成或 ZIP 打包失败时，先单独导出记录失败原因的最终 JSON，再打开打印视图保存 PDF。保存结果持续显示在工作台，刷新后仍可查看；解压核对两份文件和方案版本后交回，载入方案及研究者汇总使用解压后的 JSON。JSON 或打印视图出错会显示失败状态并恢复操作，可使用「仅备份 JSON」或重新保存。

## 版本更新与正式使用

修改文本只编辑 `M1_content/content.json`，同步可读稿和审核表，并增加 `content_version` / `study_material_version`。运行以下构建，再重新生成图片和打印文件；旧版本保留在独立受控目录。

```sh
node scripts/build.mjs
```

本包的HTML构建需要Node。PNG/PDF和M9工作簿的生成脚本保存在研究者本地完整包；更新内容后，在完整包生成并验收相关材料，再同步发布。普通走查和填写记录不需要开发依赖。

正式材料开放前，补齐以下实际记录：

1. 临床审核者对 A、B 全文本和补充顺序的签审；A 两条初始路径在中国情境下是否都适用需明确结论。必要时替换病例并重做相关材料。
2. 最终两病例选择、完整试访和必要短材料检验，验证 85 分钟流程与病例理解。
3. 伦理批准及 M8 的机构、联系人、报酬执行、存储、保存期限、删除申请期限和文件交回路径。
4. 真实部署与实际设备的访问、录屏范围、恢复、下载和交回演练。

实际审核通过后，在 JSON 顶层填写 `clinical_review_status.status="approved"`、真实 `record_id`，并将最终两个病例各自状态改为 `approved`。`node scripts/build.mjs --release` 检查临床字段；正式链接使用 `mode=study`。伦理、试访与设备记录由研究者按上述清单确认后启用。

16 场预分配采用种子 20261104 的 Mulberry32 与 Fisher–Yates 打乱：每 4 场包括 S1–S4，每个顺序覆盖四种方向配对。初始链接均为预览模式；实际排期及正式链接在 M9 中登记。


## GitHub Pages部署

仓库以`one-physician-site.zip`保存完整网站源码、固定材料和空白记录模板。GitHub Actions在main分支更新后解压，核对`deployment-manifest.json`中的SHA256，再发布至GitHub Pages。下载并解压ZIP后即可浏览目录。运行`node scripts/build.mjs`可重建当前9个HTML页面。研究数据保存在操作设备本地，按主持流程导出交回。
